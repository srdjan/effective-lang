Status: validated, 2026-10-17. Source: `docs/plans/2026-10-17-disagreements.md`,
items C7, C15, and N3, and decisions D21 and D23 of `docs/transpiler-design.md`.
Fable validated the first draft and reported 8 findings. Opus accepted all 8.
Section 3 maps each finding to its resolution.

## 1. Part 1: D21, a named diagnostic for a deep type

### Problem

`TypeTable.assignable` (`src/core/types.ts`) stops at `MAX_DEPTH = 256` and
returns false. So record types 300 levels deep, `int` to `number`, give a
false `type-mismatch/003`. A chain of type aliases can have any length,
because each alias is one declaration. So no fixed cap prevents a false
result. `flattenMembers` (`src/core/patterns.ts`) has a second silent cap of
64. The IR validator (`src/core/validate/typing.ts`) has a cap of 64 too. It
gives a false `validation/002` for a chain of 70 aliases or an inline record
100 levels deep.

### Depth

The depth D of a type is this:

- A primitive, a literal, the error type, and a provider have D = 1.
- A named type that is not an alias, that is an error or a brand, has D = 1.
- An alias name has D = 1 + D(target).
- A record, array, option, tuple, union, or function has D = 1 + the largest D
  of its children. The children of a function are its parameters and its
  result.

Each recursive call of `assignable` replaces one side by a child or an alias
target. So the number of frames is at most D(s) + D(t).

### Rules

1. A type declaration whose alias body has D > 128 gets the new diagnostic
   `declaration/012` on its name span. Then the checker defines that alias as
   the error type with `table.defineAlias(id, table.error)`, as
   `checkCycles` does for a cycle (`src/core/check.ts`). So a later comparison
   never walks the deep chain.
2. The check runs in `ModuleChecker.run` after `checkCycles()`. At that point
   every alias of the module has its definition, and `table.load` has loaded
   the imported aliases. The walk follows `table.aliasOf`, so a chain across
   modules counts.
3. The walk computes exact heights bottom-up, with a memo keyed by `TypeRef`
   for the whole module. When the running depth passes 128, the walk stops for
   that declaration and memoizes nothing for the aborted nodes. The walk uses
   loops, not closures, so its recursion stays at most 129 frames.
4. Make `checkCycles` iterative. Its recursive Tarjan `visit` overflows at
   about 4000 aliases.
5. In `assignable`, replace the `every` and `some` closures with `for` loops.
   This doubles the frames that the stack holds. Set `MAX_DEPTH` to 1536 in
   `types.ts`, in `patterns.ts`, and in `validate/typing.ts`.
6. Reason for 1536: the parser limits written nesting to 512 levels. Rule 1
   limits every alias to 128 levels. So one type has D of at most about 640,
   and two such types give at most about 1280 frames. A comment at each
   constant states this bound. Use loops in the recursive functions of
   `validate/typing.ts` too.
7. Register `declaration/012` in `src/core/diagnostics.ts`: "A type
   declaration is nested deeper than 128 levels, counting the levels inside
   its aliases."

### Acceptance

- The error fixture `fixtures/errors/declaration-type-too-deep.eff` holds a
  chain of 65 record aliases: `type A0 = { a: A1 }` to `type A63 = { a: A64 }`
  and `type A64 = { a: int }`. Then D(A0 body) = 130 and D(A1 body) = 128. One
  marker `// error: declaration/012` sits above `type A0`. The file also holds
  `export const v: A0 = { a: ... }` or another use of `A0` that gives no
  diagnostic, because `A0` is the error type. The repository keeps the file as
  plain text.
- A fast test: record types 300 levels deep, written inline in an annotation,
  `int` to `number`, give no diagnostic.
- A slow test: `build --validate` on an inline record type 100 levels deep
  gives no `validation` diagnostic.
- A fast test: 5000 aliases in a chain give `declaration/012` and no
  exception.
- The registry test in `tests/fixtures_test.ts` passes.
- `deno task check` passes.

## 2. Part 2: D23, long names and long strings at the `deno fmt` fixed point

### Problem

Decision D12 says that `deno fmt` leaves the emitted text unchanged. The
golden files and `fixtures/emit/forms/` pass, but their names are short. Probes
in `/tmp/dv/fmt` and `/tmp/dv/fmt2` show seven forms that `deno fmt` rewrites
when a name, a module path, or a string literal is long. The target text in
each row is the output of `deno fmt --no-config`.

| Form | Printer site | Emitted now | `deno fmt` output |
| --- | --- | --- | --- |
| Selector test of a match arm | `armTest`, `emit/expr.ts` | `$t0 === "long..."` on one line | `$t0 ===`, then the string on the next line, two levels deeper than the test line |
| `Schema.Literal` with a long string | `schemaOfLiterals`, `emit/types.ts` | `Schema.Literal("long...")` | `Schema.Literal(`, the string with a trailing comma, `)` |
| Brand schema | `emit/decls.ts`, the brand case | one line | `Schema.String.pipe(`, `Schema.brand(`, the string with a comma, `),`, `);` |
| Schema type alias | `emit/decls.ts`, the `typeof X.Type` line | one line past 80 columns | `export type X =`, then `typeof X.Type;` one level deeper |
| Service class header | `serviceDeclaration`, `emit/decls.ts` | the header and the tag string inline | `export class S`, then `extends Context.Service<...` one level deeper, as `errorDeclaration` does. The tag call breaks its argument |
| `Service.use` arrow | the `perform` case, `emit/expr.ts` | `$s.find(id));` | the `)` and the `;` on their own line. Give the arrow a `bodyGroup`, so `callArguments` moves the parenthesis down |
| `catchTags` key | `catchEffect`, `emit/expr.ts` | `"long#Tag": (e) =>`, then the body | `"long#Tag":`, then `(e) => body` one level deeper |

Out of scope: six forms with very long identifiers need the member-chain rule
of `deno fmt`, which `doc.ts` does not model. Three of them are a `TaggedError` type argument past 80 columns, a struct
field past 80 columns, and a long function name. The long name moves the arrow
below `=`.

The other three forms are a member access that
breaks at the dot, a `yield* Service.use(` binding, and a parameter annotation
past 80 columns. The probe thresholds are about 47 characters for an error
name and 50 for a service name. The ledger records these forms as not at a
fixed point.

### Method

1. Add a module in a deep directory under `fixtures/emit/forms/`, for example
   `a-very-long-directory-name-for-the-module-path/and-another-nested-part/long-names.eff`.
   Use the source of `/tmp/dv/fmt2` and the match arms of `/tmp/dv/fmt`. Keep
   every name at the length of the `/tmp/dv/fmt2` names, 40 to 43 characters.
   Longer names reach the out-of-scope forms.
2. Add the module to `buildForms` in `tests/emit_slow_test.ts`. Update the
   file list, the `Checked 2 files` count, and the message "both files" in the
   fixed-point test.
3. Change the printer in `src/core/emit/` until `deno fmt --check` accepts the
   new module. Every existing golden and forms file must stay byte-equal. Use
   `group`, `indent`, `line`, `soft`, `fill`, `alt`, and `bracketed` of
   `doc.ts`. Use the helpers `callArguments` and the header rule of
   `errorDeclaration`. Do not add a post-pass formatter.
4. Run `deno task golden:update`. The diff of `fixtures/golden/` must be
   empty. If it is not empty, stop and report the diff.
5. If a form cannot reach the fixed point, stop and report it with the
   `deno fmt` diff. Do not exclude files from `deno fmt`.

### Acceptance

- `deno task check` passes, with the new module in the fixed-point test and
  in the `deno check` test of the forms.
- `fixtures/golden/` is unchanged.
- The ledger rows "Not at a fixed point" in `docs/phase-a-rules.md` describe
  the new state, with the out-of-scope forms. The README sentence on the
  reachable form does too.
