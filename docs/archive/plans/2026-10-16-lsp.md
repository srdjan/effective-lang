## 2. Goal and acceptance

This phase delivers an LSP server over the core, a thin VS Code client, and the
harness for M1, M3, and M4. The phase is complete when these checks pass from
the repository root:

1. `deno task check` passes: format check, lint, type check, fast and slow tests.
2. A slow test starts the real server on a copy of `fixtures/examples`. The
   test initializes the server, opens `main.eff`, and receives an empty
   diagnostic list for it. Then it gets a hover with the contract text and a
   definition in another module. Then it saves, finds `main.ts` on disk, and
   shuts the server down with exit code 0.
3. Fast tests drive the server in process through an in-memory transport and
   cover every request and notification in section 5.
4. `deno task bench m1 m3 m4` at the quick scale ends in less than one minute
   per measurement and prints distributions with a noise floor for M1.
5. The user opens `fixtures/examples` in VS Code with the client. The user
   sees diagnostics, hover, go-to-definition, and document symbols. The user
   also sees the generated TypeScript document and the files written on save. The user does this check
   by hand. No automated test covers the client UI.

Out of scope: completion, semantic tokens, rename, references, and code
actions. The playground, Phase B, a worker thread, and cancellation inside the
core are also out of scope. So is go-to-definition from a generated `.ts` file
into `.eff` source.

## 3. Deviation from the design

Design section 2.4 recommends a per-declaration check loop with a cancellation
token. This phase keeps `Program.update` as one synchronous call and adds no
cancellation. Reason: the server handles one message at a time, so a result is
never stale when the server publishes it (section 5.5). M1 measures the stall.
If M1 shows a stall above the D9 budget, a later phase adds the loop or a worker.

## 5. Server behavior

### 5.1 Transport (`jsonrpc.ts`)

A frame is a header block and a body. The header block holds
`Content-Length: <n>` and an optional `Content-Type`, each line ends with
`\r\n`, and an empty line ends the block. `<n>` counts UTF-8 bytes of the body.
The decoder takes `Uint8Array` chunks and returns the complete messages. A chunk
can hold part of a frame or several frames.

A malformed header or a body that is not JSON is an error value, not an
exception. The encoder writes the same form.

Message shapes: request (`id`, `method`, `params`), notification (`method`,
`params`), response (`id`, `result` or `error`). Narrow incoming values from
`unknown`. Use no `any`.

Error codes: `-32700` parse error, `-32600` invalid request, `-32601` method not
found, `-32602` invalid params, `-32002` server not initialized, `-32600` for a
request after `shutdown`.

Edge cases. A body that is not JSON gets a `-32700` response with `id: null`. A
notification with an unknown method gets no response. A notification whose
method starts with `$/` is ignored. A notification before `initialize` is
dropped, except `exit`.

### 5.2 Positions (`positions.ts`)

The server announces `positionEncoding: "utf-16"`. A JavaScript string indexes
by UTF-16 code unit, so a character offset needs no conversion (design 2.3).
Line ends follow `lineStarts` in `src/core/source.ts`: `\n`, `\r\n`, or a lone
`\r`, as LSP requires. A position past the end of a line clamps to the line
end. A line past the end clamps to the text end.

URIs: convert with `fromFileUrl` and `toFileUrl` from `jsr:@std/path`. Add the
import to `deno.json`. A URI that is not `file:` is ignored.

### 5.3 Projects and the overlay (`projects.ts`)

A project is a directory that holds `effektive.json`. When a document opens,
the server walks up from its directory to the first ancestor with
`effektive.json`. The server keeps one `Program` per project root. A document
with no project gets no diagnostics, and its requests return `null`. The server
logs that once per document through `window/logMessage`.

The server keys a project by the directory path that it takes from the URI. It
does not resolve links, because `/var` and `/private/var` differ on macOS. A
`Program` lives until the server exits. An open document whose root-relative
path fails `isSourcePath` (`src/cli/workspace.ts`) has no project, as in the
disk walk. Nested projects are a known limit. `readWorkspace` of an outer root
also reads the files of an inner project, so one file can be in two programs.

When a project opens, the server reads its files with `readWorkspace` from
`src/cli/workspace.ts`. An open document overrides the disk text of its path.
`didClose` restores the disk text. When the file is not on disk, `didClose`
removes it from the program.

`workspace/didChangeWatchedFiles` with type Created (1) or Changed (2) reads
the path from disk again. Type Deleted (3) removes the path. An event for an
open document is ignored, because the editor owns that text. `effektive.json` is never an open document for the server,
because the client selects only the `effektive` language. Its changes arrive
only through watched files.

Configuration errors. When `Program.update` returns a `ConfigError`, the server
publishes the configuration diagnostic on `effektive.json` (5.5). It keeps the
last good revision for hover, definition, symbols, and generated text. It keeps
the published diagnostics of the other files. The next good update clears the
configuration diagnostic. Before the first good revision, every request on the
project returns `null`.

Host interface files. An `.effi` file that no `.eff` module imports is not in
`project.modules` (`src/core/db.ts` makes entries only from `.eff` files). For
such a file, `documentSymbols` parses the open text with `parseFileFresh`. Hover
and definition return `null`. The README states this limit.

Document sync is incremental (`TextDocumentSyncKind.Incremental`). A change
event without a range replaces the whole text. The server applies change events
in order.

### 5.4 Scheduling

A change marks its project dirty. A request on a dirty project flushes it
first, so a request never answers from an old revision. Correctness does not
depend on the flush timing. Only M1 latency does.

The stdio loop has this shape:

```ts
for await (const chunk of Deno.stdin.readable) {
  for (const message of decoder.push(chunk)) server.handle(message);
  server.afterBatch();
}
```

`afterBatch` flushes every dirty project at once when `debounceMs` is 0. With a
positive `debounceMs`, it schedules the flush again through the scheduler port.
The port is `schedule(callback, ms)` and returns a cancel handle. `shutdown`
cancels a pending flush. Do not use `setTimeout(0)` for the default, because
its order against a pending stdin read is not defined.

The in-memory transport of the fast tests has `deliver(messages)`. It calls
`handle` for each message. After the last message, it calls `afterBatch`. The default needs no timer in
tests. Tests of a positive `debounceMs` use a manual scheduler.

A flush calls `Program.update` with the changes since the last flush. It
computes and stores `revisionDelta` against the previous good revision (5.11).
Then it publishes diagnostics (5.5). Then it sends `effektive/generatedChanged`
for each subscribed module whose generated text or stale flag changed (5.8).

### 5.5 Diagnostics

After each flush, the server publishes `textDocument/publishDiagnostics` in
this order:

1. Each open document of the project, sorted by path. The server publishes an
   open document after its `didOpen`. It also publishes it after each flush
   that used a new version of it, even when the list is unchanged.
2. Each closed file whose list changed, sorted by path. A closed file whose
   list became empty gets one empty list.

A closed file with an unchanged list gets no notification. Reason: the large
synthetic project has 53 modules: 52 `.eff` modules and one `.effi` module. A
publish for every file on every change
would delay the publish that M1 waits for.

The `version` field is the version of the open document whose text the
revision used, or absent for a closed file. Because the server is synchronous,
the revision always used the latest text. A test asserts the version.

Mapping: `range` comes from the span. `severity` is 1 for error and 2 for
warning. `code` is the diagnostic code, for example `failure-contract/001`.
`source` is `effektive`. `relatedInformation` comes from the related spans. A configuration
error from `Program.update` becomes one diagnostic on `effektive.json` at line
0, character 0, with the text of `describeConfigError`.

### 5.6 Hover (`hoverAt` in `src/core/editor.ts`)

`hoverAt(revision, path, offset)` returns the span and two texts, or undefined.

1. The source contract. `hoverAt` prints its own text. It does not change
   `typeAt` or its test.
   - Function name: the text has the parameter types, for example
     `rename(id: string, name: string): User fails StoreUnavailable |
     UserMissing uses Users.find | Users.save`. Each parameter type prints with
     `table.show` of `signature.parameters[i].type.ref`. The sets print in
     sorted identity order, as `typeAt` prints them.
   - Constant name: `name: T`.
   - Any other checked node: the type and the sets, as `typeAt` prints them.
   - Where `table.show` prints `<error>`, `hoverAt` prints `unknown (error)`
     (design 6.4).
2. The backend type, only on the name of a module-level function or constant.
   It exists only when `revision.emitted(name)?.ok` is true. Then `new
   Scope(ir, config)` cannot throw. Still wrap the construction and the print in
   a `try` that maps `EmitFailure` to "not available". A throwaway `Scope` is
   safe, because `typeDoc` changes only the name tables of that `Scope`.
   - Function: print the header as `functionDeclaration` in
     `src/core/emit/decls.ts` does. The parameter names come from
     `d.parameters` and the types from `typeDoc`. The return is
     `effectTypeDoc(scope, typeDoc(scope, d.type.result), d.type.effects)` in
     effect mode, else `typeDoc(scope, d.type.result)`. An inferred contract
     uses the same rule, from `d.type`.
     Example: `(id: string, name: string): Effect.Effect<User, ...>`.
   - Constant: `typeDoc` of its type.
   - Not available: the text `backend type: not available while the module
     has errors`.

The server returns markdown: an `effektive` code block for the contract and a
`typescript` code block for the backend type. A test compares the backend line
of each explicit-contract function in `users.eff` with its header in
`fixtures/golden/users.ts`.

### 5.7 Definition and symbols (`src/core/editor.ts`)

`definitionAt(revision, path, offset)` finds the innermost syntax node at the
offset that has an entry in the module resolution `targets`. It maps the target
to a location:

- `type`, `error`, `service`, `value`, `provider`: the module from `moduleOfId`,
  the name from `nameOfId`, then the `nameSpan` of the index entry of that
  module. This covers `.effi` host interface files.
- `cap`: the `nameSpan` of the method entry of the service declaration.
- `local`: the binding span. Add `locals: ReadonlyMap<LocalId, Span>` to
  `ModuleResolution` in `src/core/resolve.ts`, filled from each local binding.
- `builtin`, `builtin-type`, `field`, `unresolved`: no location.

Add `moduleOfId`, `nameOfId`, and `methodOfCapability` to a core module, for
example `src/core/ids.ts`. The core versions return `undefined` for a malformed
identity. The emitter versions in `emit/scope.ts` call them and keep their
`internal` throw. `serviceOfCapability` already exists in `src/core/check.ts`.
`editor.ts` does not import from the emitter for identities.

A local binding identity has the form `local:<module>#<function>/<name>`, with
a `/<n>` suffix for a repeated name. `declareLocal` in `src/core/resolve.ts`
sets the `local` target on the binding's own name node. Fill `locals` there.

`documentSymbols(revision, path)` returns the index entries of the file in
source order, with service methods as children.

| Declaration | Symbol kind |
| --- | --- |
| `const` with an arrow | Function (12) |
| other `const` | Constant (14) |
| `type` | Struct (23) |
| `error` | Class (5) |
| `service` | Interface (11) |
| service method | Method (6) |
| `provider` | Variable (13) |

 A file with syntax errors still has symbols for
each declaration whose name parsed.

### 5.8 Generated TypeScript

Request `effektive/generatedTypeScript` with params `{ textDocument: { uri } }`.
The result is `{ text, stale }` or `null`. The text is the emitted module of the
current revision when it emits. Otherwise it is the last good text of that
module with `stale: true`. The result is `null` when the module never emitted in
this server session.

The first request for a module subscribes it. After each flush, the server
emits each subscribed module. When the text or the stale flag changed, it sends
the notification `effektive/generatedChanged` with `{ uri }`, where `uri` is the
`.eff` source URI.

### 5.9 Save

On `textDocument/didSave` of an `.eff` file, when `writeOnSave` is true, the
server flushes. Then it writes `<module>.ts` and `<module>.ts.map` of that
module only (design 2.1, per save). It uses `writeGenerated` (section 6). A
module with an error keeps its last good files, as `build` does. A write
failure goes to `window/logMessage` with type 1.

### 5.10 Lifecycle and options

`initialize` returns the capabilities: `positionEncoding`, incremental text
sync with `save: { includeText: false }`, `hoverProvider`, `definitionProvider`,
`documentSymbolProvider`. Every request before `initialize` gets `-32002`.
`shutdown` returns `null`. `exit` ends the process with code 0 after `shutdown`
and code 1 without it.

`initializationOptions` may hold `debounceMs` (a finite number at least 0) and
`writeOnSave` (a boolean). A missing or invalid value takes the default: 0 and
true. An invalid value is logged.

### 5.11 Statistics for M3 and M4

Request `effektive/stats` with params `{ textDocument: { uri } }`. The URI
selects the project, as for every other request. The result holds the revision
number and the modules that the last flush rechecked. It also holds the
cumulative query counts, the stored delta of the last flush, and the
`Deno.memoryUsage()` fields `rss` and `heapUsed`.

The delta has the modules whose interface hash changed and the modules whose
mode map changed. Several flushes between two stats requests
report only the last delta. The harness sends one stats request per step.

A mode flip of an exported function changes the interface hash too, because
the payload holds each exported function type with its mode
(`src/core/interface.ts`). A mode flip of a private function changes the mode
map but not the hash (correction of 2026-10-17). So only an exported mode
change is a subset of an interface change. A flip can also reach an importer: an exported
function with an explicit contract and empty sets that calls the flipped
function flips too.

A hover on a function name runs `lowered` and `emitted` on demand. So hovers
add to the `lowerings` and `emits` counts.

Query counts in `Program`: `parses` (a parse that misses the memo), `checks` (a
module checked again), `lowerings`, and `emits` (each computed on demand).
Expose them as a read-only `counts` value. Add `revisionDelta(previous, next)`
to `src/core/db.ts`. It returns the modules whose interface hash differs and the
modules whose mode map differs.

### 5.12 Entry (`main.ts`)

`deno task lsp` runs `deno run --allow-read --allow-write src/lsp/main.ts`.
The entry runs the loop of section 5.4. Log text goes to stderr and never to
stdout.

The entry writes each frame with `Deno.stdout.writeSync` in a loop until every
byte is written, because `writeSync` can return a short count on a pipe. It
never starts an un-awaited asynchronous write, because two such writes can
interleave and corrupt a frame. End of stdin ends the process: code 0 after
`shutdown`, code 1 without it.

## 8. Measurements M1, M3, M4

All three follow the protocol of the README section "Measurements". Each row is
a distribution. No number enters the docs without its floor, size, and sample
count. The quick scale of each measurement ends in less than one minute. Only
the scale parameters differ between `--quick` and `--full`.

`bench/lsp_client.ts` is a client over a spawned server process. It uses
`jsonrpc.ts`. It spawns `Deno.execPath()` with the same arguments as the VS
Code client. The project is written to a temporary directory and removed after
the run.

Edit script, one edit per step. The kinds are body, header, alias, and mode
flip. Body and header use `applyBodyEdit` and `applyInterfaceEdit` from
`bench/generate.ts`. Add `applyAliasEdit`, which changes a type alias that an
exported signature of the edited module names.

Add `applyModeFlipEdit`, which
flips the execution mode of one exported function with an explicit contract and
empty sets. Add `export const flip = (n: int): int => n + 1` to the generator
prologue next to `bump` and `extra`. The edit toggles the body between `n + 1`
and `retry(() => n + 1, { times: 1 })`. Fable confirmed with a probe that both
forms check with no diagnostic, and that the second has mode `effect`.

A test asserts for each new edit that `revisionDelta` reports the expected
change.

For the five examples, the body edit changes one literal in a function body of
`users.eff`. The implementer names the exact edit in the README.

The client reads stdout all the time while it sends. Otherwise a large response
can fill the pipe and block the synchronous server. The step counts go in
`bench/profile.ts`. Each measurement prints its elapsed time.

**M1.** Two server processes, A and B, run the same script on the same project.
The order of the sides alternates. For each step, the time runs from the send of
`didChange` to the receipt of `publishDiagnostics` for that URI and version.
The edited document is the only open document, so its publish comes first
(5.5). Then a hover on a fixed function name gives the hover round trip.

Rows: size and edit kind. Columns: the distribution and `floor %`. Inputs: the
examples and the sizes small, medium, and large.

**M3.** Over the same script, after each step, the client sends
`effektive/stats`. Rows: size and edit kind. Some columns give the median and
maximum of the per-step deltas of `parses`, `checks`, `lowerings`, and `emits`.
Two columns give the fraction of steps with an interface change and with a
mode change.

M3 runs the script without hovers, so that the counts show the flush alone.
Counts are exact, so M3 has no floor.

**M4.** Two servers, A and B, size medium. The script repeats the four kinds.
After each step, the client reads `rss`. Rows: the step count N, three values.
Columns: the peak sampled `rss` of side A and of side B, and the `rss` after
the last step.

The M4 report states that the peak is sampled only at step ends.

`deno task bench` with no name runs every measurement. `bench/main.ts` accepts
`m1`, `m3`, and `m4`.

## 10. Risks

| Risk | Signal | Response |
| --- | --- | --- |
| A stdout write that is not a frame breaks the client | Client logs a header error | All logs go to stderr or `window/logMessage`; the slow test reads every byte as frames |
| `Program.update` stalls the loop on a large project | M1 tail on size large | Record the number; a later phase decides on a worker or cancellation (section 3) |
| Deno picks the wrong config when VS Code starts the server | Import error at start | The client passes `--config` explicitly |
| The backend type in hover differs from the emitted type | A test compares hover with the golden `.ts` header of the same declaration | Print the header with the rule of `functionDeclaration` (5.6) |
| `vscode-languageclient` needs a newer engine than the installed VS Code | `npm ci` warning or activation error | Pick an older version that fits; record it |
